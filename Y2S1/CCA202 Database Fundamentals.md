# Chapter 1: Introduction to Database Systems & The Evolution of Data Processing

## 1.1 Data vs. Information: The Foundations of Knowledge

The field of database systems is rooted in the operational distinction between **raw data** and **meaningful information**:

```mermaid
flowchart LR
    Data["Raw Data<br/>(Unprocessed facts, symbols, numbers)"] --> Processing["Contextual Processing<br/>(Structuring, formatting, aggregation)"]
    Processing --> Info["Information<br/>(Processed data revealing meaning)"]
    Info --> Decision["Knowledge & Decisions<br/>(Timely, actionable insight)"]
```

> [!info] Data vs. Information
> - **Data (Raw Facts):** Unprocessed, raw observations, atomic facts, numbers, or symbols that have not yet been evaluated, organized, or contextualized to reveal their operational meaning (e.g., `37.8`, `A102`, `180024`). Data constitutes the raw building block of all information.
> - **Information:** The refined product generated by processing, structuring, formatting, and analyzing raw data to unveil its contextual significance, relationships, and implications (e.g., *"Patient temperature is 37.8°C at 14:00"* or *"Flight A102 is delayed by 45 minutes"*). High-quality information must be **accurate**, **relevant**, and **timely** to support sound organizational decision-making.

## 1.2 Database and Database Management System (DBMS) Concepts

### 1.2.1 What is a Database?
A **database** is a shared, integrated computer structure designed to store and manage a collection of:
1. **End-User Data:** Raw facts, records, and measurements of operational interest to the organization.
2. **Metadata (Data About Data):** A comprehensive description of data characteristics, data types, lengths, constraints, and relational associations linking records across the entire database structure. Metadata enables the database to be self-describing and integrated.

### 1.2.2 What is a DBMS?
A **Database Management System (DBMS)** is a complex suite of software programs that manages the physical and logical database structure, arbitrates all user and application access, and enforces system security, integrity, and operational concurrency.

```mermaid
flowchart TD
    subgraph ClientLayer["Application & User Layer"]
        U1["End Users / Web Clients"]
        App["Enterprise Application Programs (Java, Python, C++)"]
        Dev["Database Administrators / Engineers"]
    end

    subgraph DBMSLayer["DBMS Software Intermediary"]
        direction TB
        IntReq["Request Translation & Query Processor (SQL Engine)"]
        subgraph CoreEngines["DBMS Subsystem Engine"]
            direction LR
            DD["Data Dictionary"]
            Conc["Concurrency Control"]
            Sec["Security & Privacy"]
            Rec["Backup & Recovery"]
        end
        Opt["Storage & Buffer Manager (Performance Tuning)"]
        IntReq --> CoreEngines --> Opt
    end

    subgraph StorageLayer["Physical Storage Layer"]
        DBData["Integrated Database (User Data + Metadata)"]
    end

    ClientLayer <==> DBMSLayer
    DBMSLayer <==> StorageLayer
```

### 1.2.3 The Pivotal Role of the DBMS
The DBMS acts as an essential **software intermediary**:
- **Abstraction and Complexity Hiding:** Shields application developers and end users from the low-level physical complexities of disk block addressing, indexing B-trees, page swapping, and binary record serialization.
- **Data Sharing & Integrated View:** Presents each authorized user and application with an integrated, consistent, and customized view of organizational data.
- **Request Translation:** Intercepts high-level queries (such as SQL statements), translates them into low-level physical I/O commands, optimizes the execution plan, and returns structured result sets.

## 1.4 The Importance of Database Design

Database design defines the precise architecture, schema, relational constraints, and storage structures used to store and manage organizational records.
- **Well-Designed Database:** Facilitates reliable data management, enforces integrity rules, minimizes storage redundancy, and yields prompt, accurate query results for strategic decision-makers.
- **Poorly-Designed Database:** Introduces subtle, difficult-to-trace bugs, generates conflicting data copies, degrades query execution performance, and frequently produces flawed reports that lead to disastrous business decisions.

## 1.5 Evolution of Data Processing: From File Systems to Databases

To appreciate the architectural significance of modern databases, we must examine the limitations of historical file processing systems.

```mermaid
timeline
    title Evolution of File Systems to Modern Databases
    1950s : Manual File Systems : Paper file folders & physical filing cabinets : High labor overhead & manual cross-referencing
    1960s : Computerized File Systems : DP specialists write custom 3GL programs (COBOL, FORTRAN) : File-per-application architecture
    1980s : Spreadsheet Redux : Personal computer tools (Lotus 1-2-3, MS Excel) : End users manipulate data directly
    1970s-Present : Modern DBMS : Centralized logical repository : Physical and structural independence : Unified SQL standard
```

### 1.5.1 The Architecture of Early Computerized File Systems
In early computerized file processing, organizations hired **Data Processing (DP) specialists** to write custom programs (in languages like COBOL) for each specific reporting requirement. 
- The Accounting department had its own customer file and custom accounting programs.
- The Sales department maintained a separate sales file and separate programs.
- Each program defined its own internal record structure and read its dedicated sequential files directly from tape or disk.

```mermaid
flowchart TD
    subgraph TraditionalFileSystem["Traditional Computerized File System: Siloed Architecture"]
        direction LR
        ProgA["Accounting Program"] --> FileA["Accounting File<br/>(Cust_ID, Name, Balance, Address)"]
        ProgB["Sales Program"] --> FileB["Sales File<br/>(Cust_ID, Name, Credit_Limit, Address)"]
        ProgC["Shipping Program"] --> FileC["Shipping File<br/>(Cust_ID, Name, Delivery_Address)"]
    end
```

### 1.5.2 Critical Flaws and Hazards of File Systems

#### 1.5.2.1 Structural Dependence
- **Problem:** Access to data in a file system is tightly coupled to the physical and logical layout of the file itself.
- **Consequence:** If an engineer alters a file's structure (e.g., expanding a ZIP code field from 5 to 9 characters), **every single application program** that opens or reads that file must be manually rewritten, recompiled, and verified.
- **Database Contrast (Structural Independence):** In a DBMS, file structures can be modified (e.g., adding a column) without invalidating existing application programs that do not use that specific column.

#### 1.5.2.2 Data Dependence
- **Problem:** Program code contains hardwired assumptions about physical data storage characteristics (byte order, integer width, decimal formatting).
- **Consequence:** Changing storage hardware or data formatting breaks application code.
- **Database Contrast (Data Independence):** The DBMS provides a logical data abstraction; storage characteristics can change without impacting program logic.

#### 1.5.2.3 Data Redundancy and "Islands of Information"
- **Problem:** Because different departments create their own files, the same fundamental real-world data (e.g., customer name, address, contact phone) is duplicated across scattered storage locations (**islands of information**).
- **Consequences:**
  - *Storage Waste:* Identical records consume duplicate physical disk space.
  - *Data Inconsistency:* Updating a customer address in the Sales file while leaving the Accounting file unedited creates conflicting records, destroying data integrity.
  - *Data Integrity Violations:* Security permissions and validation rules are inconsistently enforced across files.

#### 1.5.2.4 Data Anomalies
Data anomalies develop when required modifications to redundant data are not executed uniformly across all files.

```mermaid
flowchart TD
    subgraph Anomalies["The Three Major Data Anomalies in File Systems"]
        direction TB
        UpAnom["1. Update Anomaly<br/>An existing customer changes phone number; updating the record<br/>in File A but missing File B leaves conflicting information."]
        InsAnom["2. Insertion Anomaly<br/>A new sales agent is hired; the system requires a Customer ID<br/>to create a record, preventing the agent from being added without a dummy customer."]
        DelAnom["3. Deletion Anomaly<br/>A customer closes their account; deleting the customer record<br/>inadvertently purges the only record of the sales agent who served them."]
    end
```

> [!warning] Detailed Anomaly Examples
> 1. **Update Anomaly:** Agent Leah changes her mobile phone number. If an operator updates her number in one customer's record but fails to update other records where Leah appears, queries produce contradictory contact details.
> 2. **Insertion Anomaly:** The company hires a new agent, Carlos. Because the file structure couples customer records to agent data, Carlos cannot be entered into the system until a customer is assigned to him.
> 3. **Deletion Anomaly:** Customer Sarah terminates her policy. Deleting Sarah's record deletes the row containing the details of Agent Marcus, erasing Marcus's employment information from the system.

## 1.6 Core Functions of a Modern DBMS

A modern DBMS eliminates the hazards of file processing through nine essential system services:

```mermaid
flowchart TD
    subgraph DBMSFunctions["The Nine Core DBMS Functions"]
        direction TB
        F1["1. Data Dictionary Management<br/>(Stores schema definitions & metadata relationships)"]
        F2["2. Data Storage Management & Tuning<br/>(Physical allocation, disk caching, performance optimization)"]
        F3["3. Data Transformation & Presentation<br/>(Translates physical formats to logical presentation)"]
        F4["4. Security Management<br/>(User authentication, role-based access control, privacy)"]
        F5["5. Multi-User Access Control<br/>(Concurrency control, ACID transaction locks)"]
        F6["6. Backup and Recovery Management<br/>(Transaction logging, automated disaster recovery)"]
        F7["7. Data Integrity Management<br/>(Foreign key referential integrity, check constraints)"]
        F8["8. Database Access Languages & APIs<br/>(SQL query execution, DDL, DML, programmatic drivers)"]
        F9["9. Database Communication Interfaces<br/>(ODBC/JDBC network listeners, web service endpoints)"]
    end
```

1. **Data Dictionary Management:** Automatically stores and maintains metadata definitions, table structures, column datatypes, and relationship constraints in a centralized system catalog.
2. **Data Storage Management:** Allocates physical storage space for data, tables, and indexes, utilizing internal performance-tuning algorithms (disk buffer caching, query optimization).
3. **Data Transformation & Presentation:** Formats incoming user inputs to conform to required database types and transforms raw internal bitstreams into human-readable representations.
4. **Security Management:** Authenticates user identities and enforces granular authorization rules restricting read, insert, update, or delete privileges.
5. **Multi-User Access Control:** Employs sophisticated locking and isolation algorithms to guarantee that concurrent users access and modify records without compromising consistency (**ACID** properties: Atomicity, Consistency, Isolation, Durability).
6. **Backup and Recovery Management:** Maintains transaction logs (`WAL` - Write-Ahead Logging) to restore the database to a verified consistent state following system crashes or power failures.
7. **Data Integrity Management:** Minimizes redundancy and enforces integrity rules (e.g., primary key uniqueness, foreign key referential integrity, datatype boundary checks).
8. **Database Access Languages & APIs:** Provides standard query languages:
   - **Data Definition Language (DDL):** Defines and alters schemas (`CREATE`, `ALTER`, `DROP`).
   - **Data Manipulation Language (DML):** Queries and updates records (`SELECT`, `INSERT`, `UPDATE`, `DELETE`).
   - **Structured Query Language (SQL):** The universal, de facto declarative standard supported across vendors.
9. **Database Communication Interfaces:** Exposes network listeners supporting connections via standard APIs (JDBC, ODBC, RESTful web services).

## 1.7 Strategic Advantages and Trade-Offs of Database Systems

| Advantages of Database Systems | Inherent Trade-Offs & Disadvantages |
| :--- | :--- |
| **Comprehensive Data Sharing:** Centralized access for diverse enterprise applications. | **Increased Upfront & Licensing Costs:** High software license fees, enterprise support contracts, and hardware requirements. |
| **Enforced Data Integrity & Consistency:** Foreign key constraints prevent invalid or orphaned records. | **Management Complexity:** Demands dedicated, highly skilled Database Administrators (DBAs). |
| **Ad-Hoc Query Capability via SQL:** Instantaneous data filtering and aggregation without custom programming. | **Maintaining Currency:** Continuous software patching, performance tuning, and schema refactoring. |
| **Structural & Data Independence:** Application code remains stable when schemas evolve. | **Vendor Dependence & Lock-In:** Migrating schemas and stored procedures between vendors incurs heavy switching costs. |
| **Centralized Security Governance:** Unified audit logs, encrypted storage, and access controls. | **Frequent Upgrade / Replacement Cycles:** Underlying hardware and database versions become obsolete rapidly. |

# Chapter 2: Data Models, Business Rules & Levels of Data Abstraction

## 2.1 Fundamentals of Data Modeling

### 2.1.1 What is a Data Model?
A **data model** is an abstract representation of real-world data structures, entity characteristics, relationships, operational constraints, and transformation rules within a specified problem domain.

> [!info] Data Model as an Architectural Blueprint
> Just as an architect constructs a physical or 3D blueprint before laying the foundation of a skyscraper, a database designer authors a data model to establish a verified blueprint before creating tables or executing DDL scripts. The data model serves as a shared communication bridge between non-technical business stakeholders and technical database engineers.

### 2.1.2 Basic Building Blocks of All Data Models
Every data model is constructed from four foundational elements:

```mermaid
flowchart LR
    subgraph BuildingBlocks["Core Data Modeling Building Blocks"]
        Entity["1. Entity<br/>(A distinguishable person, place, object, or event)"]
        Attribute["2. Attribute<br/>(A characteristic or property describing an entity)"]
        Relationship["3. Relationship<br/>(An association between entities: 1:1, 1:M, M:N)"]
        Constraint["4. Constraint<br/>(A rule or restriction placed on data values)"]
    end
    Entity --- Attribute
    Entity <===>|Associated via| Relationship
    Relationship --- Constraint
```

1. **Entity:** A distinct real-world person, place, physical object, conceptual item, or event about which the organization collects and persists data (e.g., `STUDENT`, `COURSE`, `INVOICE`).
2. **Attribute:** A specific characteristic or property that qualifies an entity (e.g., for `STUDENT`: `Student_ID`, `First_Name`, `Email`, `GPA`).
3. **Relationship:** An active or passive association linking two or more entities. Expressed via **connectivity** (cardinality):
   - **One-to-One ($1:1$):** Each instance of Entity A is associated with exactly one instance of Entity B (e.g., an employee manages at most one store; a store is managed by exactly one employee).
   - **One-to-Many ($1:M$):** Each instance of Entity A is associated with many instances of Entity B, but each instance of Entity B is associated with exactly one instance of Entity A (e.g., a customer generates many invoices; an invoice belongs to one customer).
   - **Many-to-Many ($M:N$):** Each instance of Entity A is associated with many instances of Entity B, and each instance of Entity B is associated with many instances of Entity A (e.g., a student enrolls in many classes; a class contains many students).
4. **Constraint:** A precise assertion, boundary condition, or business policy limiting allowed data values or relationships (e.g., *"A student cannot enroll in more than 4 courses per term"* or *"Account balance cannot drop below zero"*).

## 2.2 Business Rules: Bridging Business Logic to Schemas

### 2.2.1 What is a Business Rule?
A **business rule** is a brief, precise, and unambiguous statement of an organizational policy, operational procedure, or principle.

> [!info] Examples of Explicit Business Rules
> - *"A customer may generate many invoices; each invoice is generated by exactly one customer."* ($1:M$)
> - *"A customer may rent many bicycles; each bicycle is rented by only one customer at any given time."* ($1:M$)
> - *"A training session cannot be scheduled for fewer than 10 employees or more than 20 employees."* (Numerical Constraint)
> - *"A student may register for a maximum of four academic subjects in a semester."* (Participation Constraint)

### 2.2.2 Sources and Identification of Business Rules
Business rules are discovered through interviews with department managers, system users, operational manuals, company handbooks, and policy documentation. Identifying them ensures:
- A standardized, shared organizational view of data.
- Accurate discovery of entity boundaries, attribute ownership, and relationship constraints.

### 2.2.3 Translating Business Rules into Data Model Components
A database engineer translates natural-language business rules into structural elements through linguistic decomposition:

```mermaid
flowchart TD
    Rule["Natural Language Business Rule:<br/>'A Customer generates many Invoices'"]
    Noun["Nouns (Customer, Invoice)<br/>--> Entities"]
    Verb["Verb (Generates)<br/>--> Relationship (1:M)"]
    Adj["Adjectives / Descriptors<br/>--> Attributes"]

    Rule --> Noun & Verb & Adj
```

### 2.2.4 Determining Relationship Type: The Two-Question Diagnostic
To establish connectivity without ambiguity, the designer asks two bidirectional questions:
1. *How many instances of Entity B relate to exactly one instance of Entity A?*
2. *How many instances of Entity A relate to exactly one instance of Entity B?*

> [!example] Diagnostic Walkthrough: Student and Class
> - **Question 1:** How many classes can one student enroll in? **Answer:** Many.
> - **Question 2:** How many students can enroll in one class? **Answer:** Many.
> - **Conclusion:** The relationship between `STUDENT` and `CLASS` is **Many-to-Many ($M:N$)**. (In a relational database, this is implemented via a composite bridge entity).

## 2.3 Chronological Evolution of Data Models

```mermaid
timeline
    title Historical Evolution of Data Models
    1960s : Hierarchical Model : Tree structure : Parent-Child segments : 1:M only : Complex pointer paths
    1960s-1970s : Network Model : Graph structure : Handles M:N directly : DBTG Standard : Introduced DDL, DML, Schema, Subschema
    1970s : Relational Model : E.F. Codd : Tables (relations), Rows (tuples), Columns : Structural independence : Declarative SQL
    1980s : Entity-Relationship (ER) : Peter Chen : Visual ERD modeling : Communication bridge : Chen & Crow's Foot notations
    1980s-1990s : Object-Oriented (OODM) : Objects, Classes, Inheritance : UML notation : Semantic modeling for complex data
    1990s : Object/Relational & XML : Extended Relational (ORDBMS) : Hybrid databases : XML semi-structured exchange
    2000s-Present : Big Data & NoSQL : Volume, Velocity, Variety : Key-Value, Document, Columnar, Graph : High scalability & availability
```

### 2.3.1 Hierarchical Model (1960s)
- **Structure:** Modeled as an inverted tree consisting of **segments** (records). Each parent segment can have multiple child segments, but every child has **exactly one parent** ($1:M$ only).
- **Advantages:** Conceptual simplicity for rigid $1:M$ hierarchies; fast access along hardwired physical pointer chains.
- **Disadvantages:** Cannot represent $M:N$ relationships; severe structural dependence; queries require low-level navigational traversal of pointer chains; modifying tree structure invalidates all application code.

### 2.3.2 Network Model (Late 1960s – 1970s)
- **Structure:** Developed by the Database Task Group (**DBTG** / CODASYL) to represent complex real-world relationships. Modeled as a **graph** where a record (member) can have **multiple parent records** (owners), supporting $M:N$ associations.
- **Standardized Concepts (Still Used Today):**
  - **Schema:** The complete logical database definition of all records and relationships.
  - **Subschema:** The specific portion of the database seen by a particular application program (view).
  - **Data Manipulation Language (DML):** Commands to query and modify records.
  - **Data Definition Language (DDL):** Statements to define schema constructs.
- **Disadvantages:** Extreme implementation complexity; navigating pointer chains required deep technical familiarity with storage layout; inflexible to ad-hoc query requests.

### 2.3.3 The Relational Model (1970s)
Pioneered by **E. F. Codd** of IBM in 1970, the relational model revolutionized data processing by separating logical data representation from physical storage mechanisms.
- **Key Tenets:**
  - Data is represented as a collection of two-dimensional tables called **relations**.
  - Each table consists of intersecting rows (**tuples**) and columns (**attributes**).
  - Tables are completely independent from one another physically.
  - Tables are linked logically through **common attributes** (Primary Key $\leftrightarrow$ Foreign Key).
- **Relational Database Management System (RDBMS):** Implements relational algebra engines and hides physical pointer manipulation entirely behind declarative **SQL**.

```mermaid
erDiagram
    CUSTOMER ||--o{ INVOICE : generates
    CUSTOMER {
        int CUST_NUM PK
        string CUST_LNAME
        string CUST_FNAME
        string CUST_PHONE
    }
    INVOICE {
        int INV_NUM PK
        date INV_DATE
        int CUST_NUM FK
        decimal INV_AMOUNT
    }
```

- **Advantages:** Unrivaled structural independence; natural tabular view; declarative SQL removes navigational code; simplified database maintenance.
- **Disadvantages:** Substantial CPU and memory overhead; potential performance bottlenecks for complex multi-table joins at scale.

### 2.3.4 The Entity-Relationship (ER) Model (1980s)
Introduced by **Peter Chen** in 1976. Rather than replacing the relational model, the ER model complements it by serving as the dominant visual conceptual modeling standard.
- **ER Diagrams (ERD):** Graphical visual diagrams representing entities as boxes, attributes as text lists or ovals, and relationships as connecting lines with cardinality symbols (Crow's Foot or Chen notation).
- **Value:** Serves as a universally understood visual communication artifact between end users, systems analysts, and software engineers.

### 2.3.5 Object-Oriented Data Model (OODM) & Object/Relational (ORDBMS)
- **OODM:** Represents data as encapsulated **objects** combining attributes (state) and methods (behavior). Objects belong to a **class**, and classes are arranged in a **class hierarchy** with **inheritance**. Depicted using UML class diagrams.
- **Object/Relational Database Management System (ORDBMS):** Hybrid extension adding object-oriented features (inheritance, user-defined types) into established relational engines (e.g., PostgreSQL, Oracle Spatial).
- **XML & Semi-Structured Data:** Extensible Markup Language (XML) and later JSON emerged to exchange semi-structured data across distributed web architectures.

### 2.3.6 The Big Data Era & NoSQL Databases (2000s – Present)
The exponential surge in web traffic, IoT sensor streams, and social media generated datasets characterized by the **3 Vs**:
- **Volume:** Massive datasets measuring petabytes or exabytes, overwhelming single-server relational capacity.
- **Velocity:** High-frequency, millisecond-latency data ingestion streams.
- **Variety:** Diverse, evolving, and semi-structured formats (JSON documents, graphs, key-value blobs) incompatible with rigid SQL table schemas.

```mermaid
flowchart TD
    subgraph BigDataNoSQL["Big Data & NoSQL Architectures"]
        direction TB
        KV["1. Key-Value Stores<br/>(Redis, DynamoDB)<br/>Simple key-to-blob hashing; ultra-low latency"]
        Doc["2. Document Stores<br/>(MongoDB, Couchbase)<br/>Self-describing JSON/BSON documents"]
        Col["3. Column-Family Stores<br/>(Cassandra, HBase)<br/>Sparse multidimensional tabular storage"]
        Graph["4. Graph Databases<br/>(Neo4j, Amazon Neptune)<br/>Nodes, edges, and properties for interconnected data"]
    end
```

- **Core NoSQL Characteristics:**
  - Non-relational; does not require predefined schema.
  - Engineered for horizontal scale-out across clusters of commodity servers.
  - Trades strict immediate consistency (ACID) for high availability, fault tolerance, and **eventual consistency** (BASE model).
  - Supported by distributed frameworks like the **Hadoop Distributed File System (HDFS)** and **MapReduce**.

## 2.4 The ANSI/SPARC Four Levels of Data Abstraction

To ensure structural and data independence, the database design lifecycle is organized into four distinct levels of abstraction:

```mermaid
flowchart TD
    subgraph ExternalView["1. External Model (End User Views)"]
        V1["Sales View (ER Sub-diagram)"]
        V2["Accounting View (ER Sub-diagram)"]
        V3["Inventory View (ER Sub-diagram)"]
    end

    subgraph ConceptualView["2. Conceptual Model (Global Organizational View)"]
        GlobalERD["Global Conceptual Schema<br/>(Hardware & Software Independent ERD)"]
    end

    subgraph InternalView["3. Internal Model (DBMS-Specific Implementation)"]
        InternalSchema["Internal Relational Schema<br/>(SQL DDL Tables, Constraints, Foreign Keys)"]
    end

    subgraph PhysicalView["4. Physical Model (Storage Media Level)"]
        PhysicalLayout["Physical Storage Layout<br/>(Disk blocks, B+ Trees, Sector allocations)"]
    end

    ExternalView --> ConceptualView
    ConceptualView -->|Logical Design| InternalView
    InternalView -->|Physical Design| PhysicalView
```

### 2.4.1 1. The External Model (External Schema)
- **Perspective:** The localized view of the database environment as perceived by specific end-user groups or departments.
- **Characteristics:**
  - The entire database is subdivided into tailored **subschemas**.
  - The Sales department sees only customer contacts and order totals; the HR department sees employee salaries and tax IDs.
  - Represented using focused ER sub-diagrams.

### 2.4.2 2. The Conceptual Model (Conceptual Schema)
- **Perspective:** A unified, global view of the entire database representing all organizational entities, attributes, relationships, and constraints.
- **Independence:** **Software-Independent and Hardware-Independent**.
  - It does not depend on the choice of DBMS vendor (Oracle vs. PostgreSQL vs. MongoDB).
  - It does not depend on the hardware infrastructure.
- **Logical Design:** The engineering activity of translating requirements into an integrated global ER diagram.

### 2.4.3 3. The Internal Model (Internal Schema)
- **Perspective:** The representation of the database as adapted to a specific chosen database software technology (e.g., mapping the conceptual ERD into relational tables, primary/foreign key columns, datatypes, and check constraints in Oracle or PostgreSQL).
- **Independence:** **Hardware-Independent, but Software-Dependent**.
  - Changing the DBMS software requires rewriting the internal schema.
- **Logical Independence:** You can modify the internal schema (e.g., refactoring table indexes or column definitions) without altering the global conceptual model.

### 2.4.4 4. The Physical Model
- **Perspective:** Operates at the lowest level of abstraction, describing how binary records are physically organized, indexed, clustered, and stored on persistent media (magnetic platters, NVMe SSD blocks).
- **Independence:** **Physical Independence**.
  - Modifying physical storage parameters (e.g., migrating from magnetic RAID arrays to NVMe flash storage, or changing block allocation sizes) does not require changes to the internal model or application code.

# Chapter 3: The Relational Database Model: Structure, Operators, and Integrity

## 3.1 Logical View of Data and Relational Table Anatomy

### 3.1.1 Relations, Tuples, and Attributes
The **Relational Database Model** represents data logically as two-dimensional tables termed **Relations**. Conceptualized by Dr. Edgar F. Codd in 1970, the relational model decouples logical data structures from low-level physical disk layouts.

```mermaid
flowchart TD
    subgraph RelationAnatomy["Anatomy of a Relational Table (Relation)"]
        direction TB
        R_Heading["Relation Heading (Attributes / Columns)"]
        subgraph Tuples["Relation Body (Tuples / Rows / Records)"]
            T1["Tuple 1: (1001, 'Smith', 'John', 3.85)"]
            T2["Tuple 2: (1002, 'Ortega', 'Maria', 3.92)"]
            T3["Tuple 3: (1003, 'Tan', 'Wei', 3.40)"]
        end
        R_Heading --> Tuples
    end
```

- **Relation (Table):** A two-dimensional grid of rows and columns containing data describing an entity set.
- **Tuple (Row / Record):** A single horizontal row describing an individual real-world entity occurrence within the entity set.
- **Attribute (Column / Field):** A named vertical column describing a specific property, characteristic, or measurement of the entity.
- **Domain:** The set of all legal, permissible atomic values an attribute can hold (e.g., $\text{Domain}(\text{STU\_GPA}) = [0.00, 4.00]$, $\text{Domain}(\text{GENDER}) = \{'M', 'F'\}$).

#### Entity Terminology Distinctions
- **Entity:** An individual, real-world object or occurrence possessing an independent existence (corresponds to a single **tuple/row** in a table).
- **Entity Type:** A category or definition of an entity (corresponds to the **relation schema/table name**).
- **Entity Set:** The collection of all entities of a given entity type currently stored in the database (corresponds to the **entire set of rows** in a table).

---

### 3.1.2 Foundational Characteristics of a Relational Table
A properly constructed relational table satisfies eight rigorous mathematical properties:
1. **Two-Dimensional Structure:** Composed of rows (tuples) and columns (attributes).
2. **Entity Occurrence per Row:** Each row represents a single distinct entity instance within the entity set.
3. **Distinct Attribute Names:** Each column possesses a distinct, unambiguous attribute name within the relation.
4. **Data Type Uniformity:** All values in a column conform strictly to the same attribute characteristics and domain constraints.
5. **Atomic Values:** Multi-valued attributes or repeating groups are disallowed; every cell contains exactly one atomic value.
6. **Order Independence of Rows:** The sequence of rows is completely immaterial to the database engine.
7. **Order Independence of Columns:** The sequence of columns does not impact retrieval or logic.
8. **Primary Key Identification:** Every table must possess an identifying attribute or combination of attributes that uniquely identifies each row.

### 3.1.3 Relation vs. Relvar (C.J. Date Formulation)
In formal database theory, C.J. Date made the crucial theoretical distinction between a **Relation** and a **Relvar (Relation Variable)**:

```mermaid

```

- **Relvar (Relation Variable):** A named container or variable whose value is a relation. The relvar schema remains constant while its contents change.
- **Relation:** The mathematical state or value (the actual set of tuples) residing inside the relvar at any given nanosecond.

## 3.2 Relational Keys, Determination, and Functional Dependencies

### 3.2.1 Determination and Functional Dependency
The mathematical foundation of relational keys is **Determination**:

> [!info] Principle of Determination
> Determination is the state in which knowing the value of one attribute makes it possible to uniquely determine the value of another attribute. 
> 
> Notation:
> $$A \to B \quad (\text{"A functionally determines B"})$$
> - $A$ is the **Determinant**.
> - $B$ is the **Dependent**.

- **Functional Dependence:** The value of attribute $B$ is functionally dependent on attribute $A$ if each value of $A$ in the table is associated with exactly one value of $B$.
  - *Example:* $\text{STU\_NUM} \to \text{STU\_LNAME}$ (Knowing student ID 1001 unambiguously determines that their last name is "Smith").
- **Full Functional Dependence:** In a composite determinant $(A, B)$, attribute $C$ is *fully functionally dependent* on $(A, B)$ if $C$ depends on the combination $(A, B)$ but is **not** dependent on any individual subset of the determinant:
  $$(\text{ProjectNum}, \text{EmployeeNum}) \to \text{WorkingHours}$$
  Neither $\text{ProjectNum} \to \text{WorkingHours}$ nor $\text{EmployeeNum} \to \text{WorkingHours}$ holds independently; only the joint pair determines hours worked.

---

### 3.2.2 Taxonomy of Relational Database Keys

```mermaid

        direction TB
        SK["<b>1. Superkey:</b> Any attribute or combination that uniquely identifies every tuple in a relation.<br/>Determines all attributes in the row; may contain redundant attributes."]
        CK["<b>2. Candidate Key:</b> A minimal superkey without unnecessary or redundant attributes.<br/>Based on full functional dependency."]
        PK["<b>3. Primary Key (PK):</b> The chosen candidate key selected by the designer to uniquely identify tuples.<br/>Enforces Entity Integrity (strictly unique, non-null)."]
        FK["<b>4. Foreign Key (FK):</b> An attribute in one table whose values match the Primary Key in another table.<br/>Enforces Referential Integrity."]

    end
    SK -->|Minimal Subset| CK
    CK -->|Selected by Designer| PK
    PK -.->|Referenced By| FK
```

| Key Type | Formal Mathematical Definition | Real-World Database Example |
| :--- | :--- | :--- |
| **Composite Key** | A key composed of two or more attributes (multi-attribute key). | $(\text{COURSE\_CODE}, \text{SECTION\_ID})$ |
| **Superkey** | Any set of attributes $K$ such that for any two distinct tuples $t_1, t_2$, $t_1[K] \ne t_2[K]$. | $(\text{STU\_NUM})$, $(\text{STU\_NUM}, \text{STU\_LNAME})$, $(\text{STU\_NUM}, \text{EMAIL})$ |
| **Candidate Key** | A superkey $K$ such that no proper subset of $K$ is a superkey. | $\text{STU\_NUM}$, or $(\text{IC\_NUMBER})$ |
| **Primary Key (PK)**| The candidate key designated as the primary row identifier. | $\underline{\text{STU\_NUM}}$ |
| **Foreign Key (FK)** | An attribute set in relation $R_1$ that references the PK of relation $R_2$. | $\text{DEPT\_CODE}$ in $\text{STUDENT}$ referencing $\text{DEPARTMENT}$ |
| **Secondary Key** | Attributes utilized for search indexing; uniqueness is not required. | $(\text{CUS\_LNAME}, \text{CUS\_PHONE})$ |

## 3.3 Relational Integrity Rules: Entity and Referential Integrity

Relational database reliability rests upon two non-negotiable integrity constraints:

```mermaid
flowchart TD
    subgraph IntegrityRules["The Two Inviolable Relational Integrity Rules"]
        direction TB
        subgraph EntityIntegrity["1. Entity Integrity (Primary Key Constraint)"]
            EI1["Every table must possess an identifying Primary Key."]
            EI2["All Primary Key values must be strictly UNIQUE."]
            EI3["NO component of a Primary Key can ever be NULL."]
            EI4["Ensures every entity has a distinct identity in reality."]
        end
        subgraph ReferentialIntegrity["2. Referential Integrity (Foreign Key Constraint)"]
            RI1["Foreign Key values must either match an existing Primary Key value in the parent table..."]
            RI2["...OR be explicitly NULL (if the relationship is optional)."]
            RI3["Prevents orphan child records referencing phantom entities."]
        end
    end
    EntityIntegrity <==> ReferentialIntegrity
```

### The Concept of Controlled Redundancy
Relationships in relational databases are created through **common attributes** (Foreign Keys). Although a Foreign Key repeats values across multiple rows in a child table, this is **controlled redundancy**—the intentional, mathematically required mechanism that makes relational table joining possible.

### Proper Handling of Null Values
A **Null** signifies the absence of a value. It represents:
1. An unknown attribute value (e.g., student GPA not yet calculated).
2. A known but missing attribute value (e.g., customer mobile phone omitted during sign-up).
3. A "not applicable" condition (e.g., spouse name for an unmarried employee).

- **Handling Nulls:** Designers use database flags (e.g., assigning a dummy code `-99` for an unassigned agent), and enforce `NOT NULL` and `UNIQUE` constraints to prevent data corruption.

## 3.4 Relational Algebra and Set Operators

Relational algebra is a theoretical formal system for manipulating relation contents using specialized operators. Relational operators exhibit the fundamental mathematical property of **Closure**:

> [!info] The Property of Closure
> The execution of any relational algebra operator (or combination of operators) on existing relations always produces a **new relation** as its output.

```mermaid
flowchart TD
    subgraph RelationalOperators["The Eight Core Relational Algebra Operators"]
        direction TB
        subgraph UnaryOps["Unary Operators (Single Relation Input)"]
            Op1["SELECT / RESTRICT (sigma - σ): Horizontal row subsetting."]
            Op2["PROJECT (pi - π): Vertical column subsetting."]
        end
        subgraph BinarySetOps["Binary Set Operators (Requires Union-Compatibility)"]
            Op3["UNION (∪): Combines rows from two tables, excluding duplicates."]
            Op4["INTERSECT (∩): Yields only rows appearing in both tables."]
            Op5["DIFFERENCE (-): Yields rows in Table A that are not in Table B."]
        end
        subgraph ProductAndJoinOps["Multi-Table Joining & Division"]
            Op6["PRODUCT (x): Cartesian product yielding all possible row pairs."]
            Op7["JOIN (⋈): Combines relations based on matching common attributes."]
            Op8["DIVIDE (÷): Identifies dividend entities associated with all divisor rows."]
        end
    end
```

---

### 3.4.1 Detailed Breakdown of Operators

#### 3.4.1.1 SELECT (or RESTRICT) ($\sigma$)
- **Nature:** Unary horizontal filtering operator.
- **Syntax:** $\sigma_{\text{Condition}}(\text{Relation})$
- **Example:** Select all customers residing in Penang with balance $> 1000$:
  $$\sigma_{\text{CITY = 'Penang' } \land \text{ BALANCE > 1000}}(\text{CUSTOMER})$$

#### 3.4.1.2 PROJECT ($\pi$)
- **Nature:** Unary vertical attribute projection operator.
- **Syntax:** $\pi_{\text{AttributeList}}(\text{Relation})$
- **Example:** Extract only customer names and phone numbers for customer 10010:
  $$\pi_{\text{CUS\_FNAME, CUS\_LNAME, CUS\_PHONE}}(\sigma_{\text{CUS\_CODE = 10010}}(\text{CUSTOMER}))$$

#### 3.4.1.3 UNION ($\cup$), INTERSECT ($\cap$), and DIFFERENCE ($-$)
- **Mandatory Prerequisite: Union-Compatibility:** Two tables are **Union-Compatible** if and only if:
  1. They possess the exact same number of columns ($n$).
  2. Corresponding columns share compatible data types and domains ($\text{Domain}(A_i) = \text{Domain}(B_i)$ for all $1 \le i \le n$).
- **UNION ($\cup$):** Combines tuples from both relations, discarding duplicate rows ($\text{SUPPLIER} \cup \text{VENDOR}$).
- **INTERSECT ($\cap$):** Yields only tuples that exist in *both* relations simultaneously ($\text{SUPPLIER} \cap \text{VENDOR}$).
- **DIFFERENCE ($-$):** Yields all tuples residing in the first relation that do not exist in the second ($\text{SUPPLIER} - \text{VENDOR}$).

#### 3.4.1.4 PRODUCT ($\times$)
- **Nature:** Cartesian product. Pairs every tuple of Relation $R$ (cardinality $m$) with every tuple of Relation $S$ (cardinality $n$), producing a relation with $m \times n$ tuples and $\text{deg}(R) + \text{deg}(S)$ columns.

---

### 3.4.2 The Family of JOIN Operators ($\bowtie$)
The **JOIN** operator combines related data across multiple tables.

```mermaid
flowchart TD
    subgraph JoinTaxonomy["The Relational JOIN Hierarchy"]
        direction TB
        subgraph InnerJoins["1. Inner Joins (Returns Only Matched Records)"]
            direction LR
            NJ["Natural Join (⋈)<br/>3 Steps: Product -> Select common attrs -> Project out duplicate column"]
            EJ["Equijoin (=)<br/>Equality condition; preserves duplicate columns in output"]
            TJ["Theta Join (⋈_θ)<br/>Inequality condition (<, <=, >, >=, !=)"]
        end
        subgraph OuterJoins["2. Outer Joins (Preserves Unmatched Tuples with NULLs)"]
            direction LR
            LOJ["Left Outer Join<br/>Keeps all left table rows; unmatched right cells = NULL"]
            ROJ["Right Outer Join<br/>Keeps all right table rows; unmatched left cells = NULL"]
            FOJ["Full Outer Join<br/>Keeps all rows from both tables; fills gaps with NULL"]
        end
    end
```

#### The 3-Step Mechanics of a Natural Join
A **Natural Join** ($\text{CUSTOMER} \bowtie \text{AGENT}$) is mathematically derived from primitive operators:
1. **Step 1 (Cartesian Product):** Form the full product $\text{CUSTOMER} \times \text{AGENT}$.
2. **Step 2 (Selection on Common Key):** Execute $\sigma_{\text{CUSTOMER.AGENT\_CODE = AGENT.AGENT\_CODE}}(\text{CUSTOMER} \times \text{AGENT})$.
3. **Step 3 (Projection):** Project out the duplicate join column, keeping only a single copy of `AGENT_CODE`.

#### Outer Joins for Diagnosing Referential Integrity
While an Inner Join silently discards unmatched rows, a **Left Outer Join** retains every row from the left table. If a customer tuple displays `NULL` across all agent fields, it immediately alerts the database administrator to a broken relationship or missing foreign key reference.

---

### 3.4.3 The DIVIDE Operator ($\div$)
- **Nature:** Binary operator operating on a 2-column dividend relation $R(A, B)$ and a 1-column divisor relation $S(B)$.
- **Output:** A single-column relation containing all values of attribute $A$ that are paired with **every single value** of attribute $B$ in $S$.
- **Real-World Application:** Answering "all" queries: *"Find all students who have taken EVERY course required for the Computer Science major."*

## 3.5 The Data Dictionary, Controlled Redundancy, and Indexing

### 3.5.1 The Data Dictionary and System Catalog
- **Data Dictionary:** A specialized metadata repository containing detailed structural definitions of all tables, columns, data types, constraints, default values, and foreign key relationships created by database designers. Known as *"the database designer's database"*.
- **System Catalog:** An internal system data dictionary automatically managed by the DBMS, containing environmental metadata (table owners, creation timestamps, index statistics, user access permissions).

#### Resolving Homonyms and Synonyms
The data dictionary serves as the central authority to eliminate semantic naming bugs:
- **Homonym:** The same attribute name used to represent different concepts (e.g., using `NAME` for customer names and consultant names). *Resolution:* Qualify attribute names (`CUS_NAME`, `CONS_NAME`).
- **Synonym:** Different attribute names used to describe the exact same real-world characteristic (e.g., `AUTO_NO` and `CAR_ID`). *Resolution:* Standardize onto a single enterprise attribute name.

---

### 3.5.2 Controlled Redundancy: Historical Accuracy Preservation
While normalization generally eliminates redundant columns, **controlled redundancy** is deliberately introduced to preserve **Historical Accuracy**:

> [!important] The Invoice Price Case Study
> An order invoice line item table (`LINE`) stores `LINE_PRICE` alongside `PROD_CODE`, even though `PRODUCT` already contains `PROD_PRICE`.
> 
> *Why?* If the product catalog price increases tomorrow from RM 100 to RM 150, queries recalculating past revenue must read the historical price charged on the invoice date (`LINE_PRICE`), not the current volatile catalog price (`PROD_PRICE`). Omitting this controlled redundancy would retroactively and illegally corrupt past financial records.

---

### 3.5.3 Database Indexing Mechanics
An **Index** is an auxiliary data structure engineered to enable high-speed data retrieval without scanning every page of a table sequentially:
- **Anatomy:** An index consists of an **Index Key** (the ordered attribute value) and a set of **Pointers** (physical storage disk block/record IDs).
- **Complexity:** Shifts table search complexity from $O(N)$ linear scans down to $O(\log N)$ or $O(1)$ logarithmic/hash searches using balanced B+ Trees.
- **Unique Index:** An index where every index key maps to exactly one physical pointer, commonly created automatically on Primary Key columns.

## 4.1 Foundations of the Entity-Relationship (ER) Model

### 4.1.1 ER Modeling vs. The Relational Model


- **The Entity Distinction in ER Modeling:** In ER modeling, the word **Entity** refers to the **Entity Set** (the entire table), whereas a single instance is called an **Entity Occurrence** or **Instance**.

## 4.2 Attributes Classification in ER Models

Attributes describe the properties of entities, categorized across five structural dimensions:

```mermaid
flowchart TD
    subgraph AttributeTaxonomy["Taxonomy of Entity Attributes in ER Modeling"]
        direction TB
        ReqOpt["<b>1. Value Requirement:</b><br/>• <i>Required Attribute:</i> Must contain a non-null value.<br/>• <i>Optional Attribute:</i> Value may be left blank/null."]
        CompSimp["<b>2. Structural Decomposition:</b><br/>• <i>Composite Attribute:</i> Can be subdivided (e.g., Address -> Street, City, Zip).<br/>• <i>Simple Attribute:</i> Atomic, cannot be subdivided (e.g., Gender, Age)."]

```

### Resolving Multi-Valued Attributes
Multi-valued attributes violate 1st Normal Form and cannot be implemented directly in a relational table cell. Database designers evaluate two architectural solutions:
- **Flawed Option 1 (Adding Multiple Columns):** Creating `DEGREE_1`, `DEGREE_2`, `DEGREE_3`. This introduces structural rigidity, wasted storage nulls for individuals with one degree, and arbitrary limits.
- **Recommended Option 2 (Creating a Related Entity):** Spawn a new entity (`EMPLOYEE_DEGREE`) linked to `EMPLOYEE` via a $1:M$ identifying relationship.

## 4.3 Relationships: Connectivity, Cardinality, and Existence

### 4.3.1 Connectivity vs. Cardinality
- **Connectivity:** Describes the structural classification of the relationship ($1:1$, $1:M$, $M:N$).
- **Cardinality:** Quantifies the **minimum and maximum** entity occurrences that can be associated with one occurrence of the related entity, formatted as $(min, max)$:
  $$\text{PROFESSOR teaches CLASS } (1, 4)$$
  *(A professor teaches a minimum of 1 class and a maximum of 4 classes).*

```mermaid
flowchart LR
    subgraph CrowsFootSymbols["Crow's Foot Cardinality Notation Symbols"]
        direction TB
        ZeroOne["Zero or One: Optional (0, 1)"]
        OneOnly["Exactly One: Mandatory (1, 1)"]
        ZeroMany["Zero or Many: Optional Many (0, N)"]
        OneMany["One or Many: Mandatory Many (1, N)"]
    end
```

---

### 4.3.2 Relationship Strength: Weak vs. Strong Relationships
The strength of a relationship depends on how the primary key of the related child entity is constructed:

```mermaid
flowchart TD
    subgraph RelationshipStrength["Relationship Strength Categorization"]
        direction TB
        subgraph NonIdentifying["Weak (Non-Identifying) Relationship"]
            NI1["Child entity's PK does NOT contain the parent's PK."]
            NI2["Drawn as a <b>dashed line</b> in Crow's Foot ER diagrams."]
            NI3["Example: COURSE (<u>CRS_CODE</u>) and CLASS (<u>CLASS_CODE</u>, CRS_CODE)"]
        end
        subgraph Identifying["Strong (Identifying) Relationship"]
            I1["Child entity's PK CONTAINS the parent's PK as a composite component."]
            I2["Drawn as a <b>solid line</b> in Crow's Foot ER diagrams."]
            I3["Example: COURSE (<u>CRS_CODE</u>) and CLASS (<u>CRS_CODE, CLASS_SECTION</u>)"]
        end
    end
```

---

### 4.3.3 Weak Entities
A **Weak Entity** is an entity that meets two mandatory conditions:
1. **Existence Dependence:** It cannot exist in the database without being associated with a parent entity.
2. **Derived Primary Key:** Its primary key is partially or totally derived from the parent entity (its PK contains the parent's PK).

> [!tip] Case Study: Building and Room
> A `ROOM` cannot exist without a `BUILDING`. In a university, room number `101` exists in multiple buildings. Therefore, `ROOM` is a **Weak Entity** whose composite PK is $(\underline{\text{BLDG\_CODE, ROOM\_NUM}})$, linked to `BUILDING` via a **Strong (Identifying) Relationship**.

---

### 4.3.4 Relationship Participation: Optional vs. Mandatory
- **Optional Participation:** An entity occurrence does not require a corresponding entity occurrence in the relationship (minimum cardinality = $0$). Represented by a small circle ($O$) on the Crow's Foot line.
- **Mandatory Participation:** An entity occurrence strictly requires at least one corresponding entity occurrence (minimum cardinality $\ge 1$). Represented by a vertical bar ($|$) on the Crow's Foot line.

---

## 4.4 Relationship Degrees and Recursive Topologies

The **Degree** of a relationship indicates the number of participating entity sets:

```mermaid

        end

```

### Recursive Relationships
A recursive relationship occurs when an entity is associated with occurrences of itself:
- **1:1 Unary:** An `EMPLOYEE` is married to zero or one `EMPLOYEE`.
- **1:M Unary:** An `EMPLOYEE` manages many `EMPLOYEE`s; each employee is managed by one manager.
- **M:N Unary:** A `COURSE` has many `COURSE`s as prerequisites, and a `COURSE` can be a prerequisite to many `COURSE`s.

## 4.5 Resolving M:N Relationships with Associative Entities

Relational database tables cannot implement $M:N$ relationships directly. An $M:N$ relationship is systematically decomposed into two $1:M$ relationships using an **Associative Entity** (also termed a **Composite Entity** or **Bridge Entity**):

```mermaid
flowchart LR
    subgraph DirectMN["Direct Conceptual M:N Relationship (Unsupported in RDBMS)"]
        STUDENT["STUDENT"] <===>|M:N| CLASS["CLASS"]
    end

    subgraph ResolvedMN["Decomposed Relational Architecture (Bridge Entity)"]
        direction LR
        S["STUDENT<br/><u>STU_NUM</u>"] -->|1:M| ENROLL["ENROLL (Bridge Entity)<br/><u>STU_NUM, CLASS_CODE</u><br/>ENROLL_GRADE, ENROLL_DATE"]
        CLASS_T["CLASS<br/><u>CLASS_CODE</u>"] -->|1:M| ENROLL
    end

    DirectMN ==>|Decompose via Bridge| ResolvedMN
```

- **Anatomy of a Bridge Entity:**
  1. Primary Key is composite, composed of the Foreign Keys referencing the two parent entities.
  2. Inherits a $1:M$ relationship from *both* parent entities.
  3. Can store independent payload attributes describing the transaction (e.g., `ENROLL_GRADE`, `ENROLL_DATE`).
